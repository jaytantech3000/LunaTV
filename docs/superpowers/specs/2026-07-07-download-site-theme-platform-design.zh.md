# LunaTV 下载站暗夜主题与平台高亮设计

**目标**

在现有 `download-site/` 静态下载站上补两个增量能力：

- 顶部增加暗夜主题切换按钮，放在中英切换按钮左侧
- 根据访问设备平台高亮对应下载项和下载按钮，优先突出当前系统最可能需要的安装包

**为什么现在做**

当前下载站已经有：

- 稳定版 / 预发布版分区
- 中英文文案切换
- 展开式版本卡片和下载列表

但仍有两个明显缺口：

- 页面只有单主题，夜间浏览对比度和舒适度不足
- 所有安装包视觉权重一致，用户需要自己扫一遍列表判断该点哪一个

这会降低首屏决策效率，也不符合“渐进增强”这一类静态下载页的常见最佳实践。

**范围**

- 增加一个顶部主题 icon 按钮
- 支持浅色 / 暗夜两种主题
- 首次访问时跟随系统 `prefers-color-scheme`
- 用户手动切换后将主题偏好持久化到 `localStorage`
- 渲染下载列表时识别当前访问平台
- 对命中的下载项和下载按钮增加高亮态
- 为主题切换和平台高亮补充自动化测试

**不做**

- 不做三态主题切换（浅色 / 暗夜 / 跟随系统）
- 不做跨页面或跨子域主题同步
- 不做 UA 精细到芯片架构级别的下载推荐
- 不新增平台筛选器、平台分组区块或浮层引导
- 不改动 release 数据结构

**现状结论**

当前实现已经具备适合增量扩展的边界：

1. `download-site/assets/app.js`
   - 已集中管理 locale 状态、渲染流程和 `localStorage` 读写
2. `download-site/assets/app.css`
   - 已使用 CSS 变量组织整页配色，适合通过 `html[data-theme]` 做主题覆写
3. `src/lib/download-site-ui.test.ts`
   - 已覆盖下载站核心 DOM 交互，适合继续补主题与平台识别回归测试

结论：

- 这次改动不需要引入框架或状态库，继续保持原生 JS + CSS 变量即可，符合 KISS / YAGNI

**实现方案对比**

1. 推荐方案：`html[data-theme]` + CSS 变量覆写 + 平台命中样式类
   - 优点：状态单一、DOM 边界清晰、最容易测试
   - 缺点：需要在初始化时补一层主题和平台推断逻辑
2. 备选方案：仅依赖 `prefers-color-scheme`，手动切换时临时覆写 class
   - 优点：初始代码略少
   - 缺点：系统偏好与用户偏好优先级更难维护，测试也更分散
3. 不推荐方案：扩展成完整“主题设置中心”
   - 优点：可扩展性更强
   - 缺点：明显超出下载页需求，是过度设计

**推荐方案**

采用方案 1：

- 主题状态挂在 `document.documentElement.dataset.theme`
- 用户偏好通过新的 `localStorage` key 持久化
- 没有用户偏好时，按系统深色偏好决定初始主题
- 平台命中结果在渲染下载项时写入 `data-platform-match="true"`

**页面结构变更**

顶部工具区调整为：

- GitHub Releases 链接
- 主题切换 icon 按钮
- 中英切换按钮组

主题按钮保持单按钮切换，不引入额外文案块，避免把当前简洁工具区做重。

**主题模型**

新增主题状态：

```ts
interface ThemeState {
  mode: 'light' | 'dark';
  source: 'system' | 'user';
}
```

行为约束：

- 初始化时先读 `localStorage`
- 若未读到用户偏好，则回退到 `matchMedia('(prefers-color-scheme: dark)')`
- 用户点击主题按钮后，立即写入 `localStorage`，并将 `source` 视为 `user`
- 当 `source = system` 时，如果系统主题在页面打开期间变化，页面应同步更新
- 当 `source = user` 时，系统主题变化不覆盖用户手动选择

这是典型的“用户偏好优先于系统偏好”模式，比只靠媒体查询更稳健。

**平台识别**

平台识别按以下优先级执行：

1. `navigator.userAgentData?.platform`
2. `navigator.platform`
3. `navigator.userAgent`

归一化结果只返回：

- `windows`
- `macos`
- `linux`
- `unknown`

显式约束：

- iPhone / iPad / Android 统一返回 `unknown`
- 不区分 `x64`、`arm64`
- 无法可靠判断的平台不高亮，保持默认样式

**资源命中规则**

下载项是否命中当前平台，使用 `fileName` 与 `platformLabel` 双重判断：

- `windows`
  - 命中 `windows`、`.exe`、`setup`
- `macos`
  - 命中 `macos`、`osx`、`.dmg`、`.app.tar.gz`
- `linux`
  - 命中 `linux`、`.AppImage`、`.deb`、`.rpm`、`.tar.gz`

若 `platformLabel` 与 `fileName` 任一命中，则视为平台匹配。

这样做的原因：

- 当前 release 数据已经包含 `platformLabel`
- 文件名匹配可作为防御性兜底，避免单一字段不稳定导致高亮失效

**视觉表现**

主题层面：

- 保留现有“纸面台账”风格，不推翻版式
- 浅色主题维持当前暖纸色方向
- 暗夜主题改为深蓝灰背景、低亮度面板、浅色文字、暖橙强调色

平台高亮层面：

- 命中的下载项提高边框对比度和背景层次
- 命中的平台标签增加更强填充
- 命中的下载按钮改为实心强调按钮
- 非命中项维持现有低干扰样式

原则：

- 只突出一个层级，不改列表排序，不制造多个同等强烈的视觉焦点

**可访问性与交互**

- 主题按钮必须有 `aria-label`
- 主题按钮应暴露 `aria-pressed`
- 焦点态继续沿用当前高可见 outline
- 不依赖颜色作为唯一识别手段，平台高亮同时通过边框、背景和按钮形态表达
- 保持移动端单列布局，不因高亮增加额外换行错位

**错误处理与容错**

- `localStorage` 不可用时，主题切换仍应即时生效，但不保证持久化
- `matchMedia` 不可用时，默认回退到浅色主题
- 平台识别失败时，不抛错，按 `unknown` 处理
- 资产缺少 `fileName` 或 `platformLabel` 时，匹配逻辑必须安全返回未命中

禁止空 `catch` 吞掉行为变化；即使静默降级，也要保证代码路径明确。

**测试策略**

先补失败测试，再实现：

1. 主题测试
   - 无用户偏好且系统深色时，初始化应进入暗夜主题
   - 点击主题按钮后，应切换主题并写入 `localStorage`
2. 平台高亮测试
   - Windows 访问时，Windows 安装包项应带高亮标记
   - 非 Windows 资源不应误命中

测试继续放在 `src/lib/download-site-ui.test.ts`，不新增测试框架。

**验收标准**

- 顶部在语言切换左侧出现主题 icon 按钮
- 首次访问时可跟随系统浅深色偏好
- 用户切换主题后，刷新页面仍保持上次选择
- Windows / macOS / Linux 访问时，对应安装包下载项和按钮有明显高亮
- 未识别平台时页面正常渲染，不出现错误或错误高亮
- 现有中英文切换与 release tab 交互不回归
